The claim object contains all the information required to send a claim to an insurer:

- insurer
- patient details
- primary member details (can be same as patient details)
- list of services

During claim submission, the API validates the claim payload against known insurer requirements and will reject claims that we know will be rejected by the insurer. However, this does not guarantee the opposite; a claim accepted by the API can still be rejected by the insurer.

Insurers can change their claim requirements without notifying us. When this happens, as soon as we understand the new requirements, we will update the validation rules and inform you. It is advisable to be prepared to adopt the updated rules as quickly as possible.

## Request Parameters

The main fields of claim are:

- `patient`: JSON object, representing patient details
- `primary_member`: JSON object, representing primary patient member
- `services`: list of JSON objects, representing services that can be reimbursed
- `status`: Claim status - `draft` or `ready` (default). Use `draft` to create a claim for manual review in the Anagram web app and manual submission.

Both `patient` and `primary_member` must be provided even if the claim is created for a primary member. In this case, both the `patient` object and `primary_member` object must contain the same data.

## Receipt

Insurers that take an itemized receipt from the practice, such as EyeMed, get it with the claim. Anagram builds the receipt from the claim's details with the receipt template of the claim's location: the layout of the practice management system set for the location, or a template Anagram has set up for your organization. The [List Locations](/api-reference/endpoint/locations) endpoint shows the system and the template of each location. When the location has no template, the claim carries the invoice Anagram generates.

To send the receipt the practice printed for the patient instead, upload its files with the [Upload Claim Receipt](/api-reference/endpoint/upload_claim_receipt) endpoint, one file per request, and pass the returned `upload_uid` values in `receipt_upload_uids`. An uploaded receipt always goes instead of the template. Pass it only for an insurer that takes a receipt.

The files go into the claim in the order of the list: a PDF with all its pages, an image as a page of its own. A claim takes up to 5 files, with up to 15 MB and 20 pages in total. An image counts as one page and as 2 MB, whatever its size. Each file has its own limits too, see [Upload Claim Receipt](/api-reference/endpoint/upload_claim_receipt).

The older `receipt_upload_uid` field with one `upload_uid` still works, so existing integrations don't need to change. Pass one of the two fields, not both. Passing `null` or an empty list is the same as passing no receipt.

An insurer can require the receipt. A claim for such an insurer from a location without a template can be created as `ready` only with an uploaded receipt. Without one, the API rejects it with `This insurer needs the itemized receipt you gave the patient. Upload it to send this claim.` Create the claim as a `draft` instead, and the practice can finish it in the Anagram web app. A draft that isn't finished within a week is deleted.

The receipt can't be changed through the API once the claim is created. If the claim isn't created, for example because of a validation error, its uploads stay available and can be passed again.

### Receipt errors

An error about one of the listed files comes under its position in `receipt_upload_uids`, counted from 0:

- `This receipt upload is unknown, expired or already used.`
- `The same file is listed twice.`

An error about the list as a whole comes under `$` in `receipt_upload_uids`:

- `A claim can have up to 5 receipt files.`
- `The receipt files are too large together. The limit is 15 MB, and an image counts as 2 MB.`
- `The receipt files have too many pages together. The limit is 20.`
- `Claims for this insurer don't take a custom receipt.`
- `Pass the receipt files as a list.` when `receipt_upload_uids` isn't a list

An error about the file passed as `receipt_upload_uid` comes under `$` in `receipt_upload_uid`. When both fields are passed, the claim is rejected with `Pass receipt_upload_uid or receipt_upload_uids, not both.` under `$` at the top level of `errors`.

For example, when the second file in the list has expired:

```json
{
    "errors": {
        "receipt_upload_uids": {
            "1": {
                "$": ["This receipt upload is unknown, expired or already used."]
            }
        }
    }
}
```
